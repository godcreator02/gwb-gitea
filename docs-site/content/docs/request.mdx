**本页回答**：一次 `gitea.http` 调用在插件里经过哪几步、每一步的规则是什么、为什么这样定；代码分在哪些文件。

## 代码分在哪些文件

{/* tree dir="../plugins/gitea/src" depth="1" hash="3e0bc2df438c" */}

`core.ts` 放不碰网络、不读磁盘、不读设置的纯函数：参数检查、URL 拼接、回执整理、脱敏，给输入看输出，测试在
`tests/core.test.ts`。`index.ts` 登记命令与设置，处理函数在这里读设置、读文件、发请求。依赖只有一个方向：
`index.ts` 引 `core.ts`，`core.ts` 只引 `vocab.ts` 里的 `isRecord`。
`service.ts` 是给别的插件 inject 的服务 `gwbGitea`，自己不发请求：`index.ts` 把发送函数交给它，命令和服务走的是同一个。
`push-mirror.ts` 是命令 `gitea.push-mirror.add` 的纯函数：检查参数、组装发给 gitea 的请求、从 gitea 的回应里挑回执字段，引 `core.ts` 与 `vocab.ts`；
它的处理函数也在 `index.ts`，最后同样交给发送函数，见本页最后一节。

{/* ref file="../plugins/gitea/src/core.ts" lines="1-1" hash="4747612b10de" blob="fc2fe60ce1ee" */}

下面用同一个例子走完全程：往一个 release 上传产物。

```json
{ "method": "post", "path": "/api/v1/repos/godcreator/gwb/releases/7/assets",
  "query": { "name": "gwb-setup.exe" }, "file": { "path": "D:\\out\\gwb-setup.exe" } }
```

## 1. 检查参数

`parseArgs` 把 `unknown` 收窄成 `HttpArgs`。method 转成大写后要在六个之内（例子里的 `post` 变成 `POST`）；path 不能为空；
query 的值只能是字符串、数字、布尔；GET、HEAD 不能带 body 或 file——node 的 `fetch` 遇到这种请求直接抛 `TypeError`，
在这一步拦下能给出看得懂的原因；带 file 时 body 只能是对象，因为它要拆成表单字段。

{/* ref file="../plugins/gitea/src/core.ts" lines="16-18" hash="3323f61f306b" blob="e78ff229a1a8" */}

检查不过的报错文字就是用法：说清哪个参数、要什么、收到了什么。agent 读报错就能改对，不必再去查 `usage`。

## 2. 组成 URL

path 去掉开头的斜杠，调用方多写了 `api/v1/` 也去掉（例子里剩下 `repos/godcreator/gwb/releases/7/assets`）。
只去掉一次：去掉后仍以 `api/v1/` 开头的，是调用方真的要访问这个路径。

{/* ref file="../plugins/gitea/src/core.ts" lines="30-35" hash="77553e37301f" blob="e78ff229a1a8" */}

`base-url` 去掉末尾斜杠，没写协议的按 `https://` 补上，这一条沿用前身 god-gitea 只走 https 的约定。
然后组成 `<base-url>/api/v1/<path>`，query 用 `URLSearchParams` 编码接在后面，query 为空时不留问号。

{/* ref file="../plugins/gitea/src/core.ts" lines="97-101" hash="12448936aef4" blob="e78ff229a1a8" */}

## 3. 组装请求体

- 带 `file`：body 的每个字段放进表单，不是字符串的先 `JSON.stringify`；文件从磁盘读进字段 `file.field`（缺省 `attachment`），
  文件名缺省取路径的最后一段。gitea 上传 release 附件要的就是 `attachment` 这个字段
- 只带 `body`：序列化成 JSON，头写 `content-type: application/json`
- 都没有：不带请求体

设置里有 token 就加头 `authorization: token <token>`，没有就不加。

{/* ref file="../plugins/gitea/src/index.ts" lines="60-75" hash="c6e12bbbb5de" blob="0849a65c26fe" */}

## 4. 发出

普通调用 60 秒超时，带 `file` 的 10 分钟：上传大文件时，传到一半被超时打断比传得慢更糟，所以上传给足时间。

{/* ref file="../plugins/gitea/src/core.ts" lines="11-12" hash="4c49074ab753" blob="e78ff229a1a8" */}

## 5. 整理回执

回应的文本超过 64KB（`BODY_LIMIT`）就截断，回执里 `truncated: true` 并带一句 `note`，提示用 query 分页重取。
插件不替调用方翻页：要哪几页、每页多少由调用方决定。截断后的 JSON 解不开，所以截断了一律按文本交回。

没截断时，满足任一条就试着按 JSON 解析：`content-type` 里有 `json`，或者去掉开头空白后第一个字符是 `{` 或 `[`。
解析失败（半截 JSON、错误页）按文本交回。gitea 的 API 全部返回 JSON，按文本交回只用于意外情况。

{/* ref file="../plugins/gitea/src/core.ts" lines="114-131" hash="60c8f4834688" blob="e78ff229a1a8" */}

回执形状是 `{ ok: true, data: { status, truncated, note?, body } }`。2xx、4xx、5xx 都走这一条：请求发出去了、
gitea 回了话，状态码怎么解释由调用方决定。日志同时记一行：method、path（不含 query）、状态码，截断了再注明一句；
token 与请求体都不进日志。

{/* ref file="../plugins/gitea/src/index.ts" lines="94-99" hash="0abc7df82136" blob="0849a65c26fe" */}

## 6. 没发出去

网络不通、地址错、超时、文件读不到，都在处理函数的 `catch` 里变成 `{ ok: false, error }`。报错文字带上异常的调用栈，
先经 `redact` 把 token 的每次出现换成 `***`，再附上检查方向：网络、`gitea.base-url` 当前的值、`gitea.token`、`file.path`。

{/* ref file="../plugins/gitea/src/index.ts" lines="100-106" hash="04540c1ba390" blob="0849a65c26fe" */}

在 `gitea.http` 里 `redact` 只用在这里。gitea 正常返回的 body 原样交回，插件不在里面找 token：token 只在请求头里发出，
gitea 的回应不会把它带回来。调用方自己把 token 写进 path、query 或 body 的，插件不替它遮掉。

## 推送镜像：gitea.push-mirror.add

开推送镜像要把 GitHub token 放进发给 gitea 的 body。这个 token 只由用户在设置界面填进 `gitea.github-token`，
agent 的参数里不能有它，所以开镜像是一条单独的命令，不是一次 `gitea.http` 调用。它和 `gitea.http` 的不同都在发送前后，中间仍是同一个发送函数：

1. **检查参数**。只收 `repo` 与 `github` 两个参数，都要写成 `owner/name`；缺了、格式不对、多了认不出的参数都直接报错，不发请求

{/* ref file="../plugins/gitea/src/push-mirror.ts" lines="51-60" hash="56258f2a9751" blob="46ec768c6174" */}

2. **读 GitHub token**。设置里没有就报错，写明请用户去设置界面填哪一项，不发请求

{/* ref file="../plugins/gitea/src/index.ts" lines="165-179" hash="13d620551ab8" blob="0849a65c26fe" */}
3. **组装请求**。`POST repos/<repo>/push_mirrors`，body 里写 GitHub 仓的地址、用户名（GitHub 只认 token，用户名写仓的 owner）、token、
   同步间隔 1 小时、gitea 上每次推送后也同步。请求照常带 gitea token 的请求头，所以 gitea token 要有这个仓的管理权限

{/* ref file="../plugins/gitea/src/push-mirror.ts" lines="63-76" hash="da239b9c05d5" blob="46ec768c6174" */}

4. **读回应**。`gitea.http` 把 4xx、5xx 照样交回；这条命令把非 2xx 当成失败，报错带状态码与 gitea 的 `message`。
   2xx 时不交回整个 body，只挑白名单里的字段，字符串值里出现的 GitHub token 换成 `***`，报错文字也一样。
   gitea 的回应本不带密码，白名单与替换保证即使它带了，token 也不会出现在回执里

{/* ref file="../plugins/gitea/src/push-mirror.ts" lines="78-94" hash="500ca64b2b82" blob="46ec768c6174" */}

日志仍只有发送函数记的那一行：method、path、状态码，body 不进日志。
